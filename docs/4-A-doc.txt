  costoRiegoUsd        costo_riego_usd         DECIMAL(10,2) NULL
  costoOtrosUsd        costo_otros_usd         DECIMAL(10,2) NULL
  creadoEn             creado_en               DATETIME(3) default now()
  Índice: (usuario_id, creado_en), para GET /siembras por dueño (4-D).

4.3 Decisiones de diseño tomadas
  1. Enums y no cadenas: son 3 granos fijos en la propuesta;
     continuacion.md permitía cualquiera de las dos opciones. Costo:
     agregar un cultivo exige migración.
  2. areaMz como Decimal y no Float, por la convención de no usar
     flotantes con áreas. Los km² no se guardan (Info_Datos_CENTA.md
     ya establece que se calcula, no se guarda); el formulario
     convierte a manzanas (HA_POR_MANZANA = 0.7).
  3. cantidadSemilla/unidadSemilla son nulas en BD: la obligatoriedad se
     valida en 4-D, no en el esquema.
  4. inversionTotalUsd es obligatoria y el desglose es nulo, para que el
     total y las partes no se contradigan en el esquema. 4-D debe
     validar que la suma del desglose no exceda el total.
  5. Moneda: dólares (USD), sufijo `Usd` en los nombres.
  6. ON DELETE RESTRICT (por defecto de Prisma): no se podrá borrar un
     usuario o distrito que tenga siembras.

9. PROBLEMAS ENCONTRADOS (candidatos a gotchas.md)
------------------------------------------------------------

9.1 Crash de libuv en Windows al cerrar pruebas HTTP
  Síntoma: `npm run pruebas:http` pasa sus 3 casos y termina con
  "Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file
  src\win\async.c, line 94". `npm test` se corta en ese punto.
  Causa probable: src/comun/http-errores.pruebas.ts llama
  `process.exit(...)` justo después de `servidor.close(...)`; en Windows
  eso dispara la aserción de libuv. La rama de 4-A parte de f6a06a4 (igual a
  origin/main) y no modifica código ni pruebas, solo schema.prisma y una
  migración; por eso la falla ya existe en main en Windows con esta
  configuración. La versión de Node no se registró.
  Solución propuesta (NO aplicada, fuera del alcance de 4-A): reemplazar
  `process.exit(fallos > 0 ? 1 : 0)` por
  `process.exitCode = fallos > 0 ? 1 : 0` en un PR aparte
  (fix/pruebas-exit-windows). Revisar si otras pruebas usan el mismo
  patrón.
  Mientras tanto: correr los grupos de pruebas por separado.

9.2 `main` local desactualizado con cambios en staging
  Síntoma: `git checkout main` mostraba archivos A/M (clima, docs) y
  "Your branch and 'origin/main' have diverged, 1 and 79 different
  commits"; `git pull origin main` fallaba por cambios locales que se
  sobrescribirían.
  Causa: el main local estaba 79 commits atrás y con archivos en staging
  del trabajo viejo de clima, que ya estaba en origin/main.
  Solución aplicada: crear la rama de 4-A directamente desde
  origin/main. La rama quedó en f6a06a4 igual que origin/main.
  Después, `git checkout main` falló por backend/package-lock.json
  modificado: se descartó con `git restore`.
  Regla: antes de empezar un punto, `git fetch origin` y crear la rama
  con `git checkout -b <rama> origin/main`.

9.3 VS Code mostraba y guardaba una versión vieja de schema.prisma
  Síntoma: el editor mostraba un schema sin CondicionDistrito (diff con
  todo el bloque de clima en rojo y panel izquierdo no editable);
  al guardar: "El contenido del archivo es más reciente".
  Causa: el editor tenía una copia en memoria desactualizada respecto
  al disco, después de cambiar de rama y restaurar el archivo.
  Efecto en cadena: la primera `prisma migrate dev` solo aplicó
  add_condicion_distrito y dijo "in sync", porque el bloque Siembra no
  se había guardado. No se creó add_siembras hasta repetir la edición.
  Solución: no pulsar "Sobrescribir"; elegir "Revertir"/"Comparar",
  cerrar las pestañas de schema.prisma (Ctrl+K y luego W), `git restore
  backend/prisma/schema.prisma`, reabrir y volver a editar.
  Verificación obligatoria antes de migrar: `git diff --stat
  backend/prisma/schema.prisma` debe mostrar solo inserciones.
  Si `migrate dev` no dice "Applying migration ..._<nombre>", la
  migración nueva NO se creó.

9.3.b Repositorio dentro de OneDrive
  El repo está en OneDrive\Imágenes\Documentos. OneDrive sincroniza en
  segundo plano y puede dejar copias viejas o bloquear cambios de Git.
  Sospechado como causa de 9.3; no confirmado. Recomendación: mover el
  repo fuera de OneDrive (ej. C:\dev\agroalerta-sv) o pausar la
  sincronización mientras se trabaja.

9.4 Ruido de finales de línea en migration_lock.toml y package-lock.json
  `git status` marcaba modified backend/package-lock.json (por
  `npm install`) y backend/prisma/migrations/migration_lock.toml.
  `git diff` de migration_lock.toml salió vacío: ruido CRLF/LF. Ambos se
  descartaron con `git restore` y no se commitearon.
  Coincide con gotchas.md 1.7 (ruido de saltos de línea en Windows).

9.5 Errores de rutas en PowerShell
  `git add backend/prisma/...` fallaba con "backend/backend/prisma"
  porque el prompt estaba en agroalerta-sv\backend y no en la raíz.
  Además, `head` y `grep` no existen en PowerShell
  (usar `git log --oneline -3` y `Select-String`). Y un comando pegado
  dos veces seguidas produjo `package-lock.jsongit restore` (ejecutar
  una línea por vez).
