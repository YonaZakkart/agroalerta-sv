1. RESUMEN DE LA IDEA
Plataforma web orientada a eventos (EDA) para prevención de riesgos agrícolas en el departamento de Morazán, El Salvador.
Integra:
- Viabilidad de cultivo por distrito (referencia CENTA: potencial de maíz, frijol y maicillo y riesgo de sequía, como área por clase)
- Monitoreo climático (Open-Meteo)
- Estimación de cosecha e ingresos basada en reglas
- Recomendaciones automáticas ante cambios climáticos o nuevos registros de siembra

El sistema reacciona automáticamente a eventos (registro de siembra, actualización meteorológica, cambio de condición climática) sin que el usuario tenga que solicitar el recálculo manualmente.

Nota geográfica (desde RAMA 2): tras la reorganización territorial, el departamento de Morazán tiene solo 2 municipios (Morazán Norte y Morazán Sur). Los 26 antiguos municipios (Chilanga, etc.) son ahora DISTRITOS. El sistema trabaja a nivel de distrito, porque es la unidad que importa para zonas de viabilidad y estaciones climáticas. El campo del usuario se llama "distrito" (ya no "municipio"). Ver detalle en RAMA 2.
Desde RAMA 12 el catálogo Municipio (2) / Distrito (26) existe como modelos en la base (el código CENTA 1301 a 1326 es la llave del distrito), y, desde RAMA 14, cargado con los datos de CENTA (26 distritos: 11 en Morazán Norte y 15 en Morazán Sur)

3. HERRAMIENTAS Y TECNOLOGÍAS (DEFINITIVAS)
- Lenguaje principal: TypeScript
- Backend: Node.js + Express + EventEmitter nativo (definido; se descartan Laravel, Django y NestJS como alternativas)
- Frontend: Angular
- API Climática: Open-Meteo
- Base de datos: MySQL
- ORM: Prisma, fijado en la versión 7.10.0 (prisma y @prisma/client) — ver nota de versión más abajo y detalle en RAMA 1
- Driver adapter de base de datos: @prisma/adapter-mariadb (obligatorio en Prisma 7 para proveedores SQL, usado tanto para MySQL como MariaDB)
- Conexión (desde RAMA 10): el adapter se construye en config/prisma.ts parseando DATABASE_URL, con allowPublicKeyRetrieval activo salvo NODE_ENV=production. Producción: definir TLS hacia la base (Parte 7).
- Autenticación: correo + contraseña + DUI hasheado + verificación por correo
  - Contraseña: argon2id, paquete argon2@0.45.1 (decidido en RAMA 2)
  - DUI: HMAC-SHA256 con secreto de servidor (DUI_PEPPER en .env), NO bcrypt/argon2 (decidido en RAMA 2, ver justificación y desviación del Mapa en esa sección)
  - Sesión: JWT stateless HS256 con jsonwebtoken (decidido en RAMA 6). Secreto JWT_SECRET (mín. 32 caracteres) y expiración JWT_EXPIRES_IN (por defecto 2h) en .env. Sin revocación: el middleware no consulta la BD.
- Despliegue: Docker
- Control de versiones: Git + GitHub (flujo por ramas + PR)
- Entorno de desarrollo de base de datos: MySQL vía Docker (contenedor local por integrante, sin instancia compartida) — ver docker-compose.yml en la raíz
- Datos de viabilidad (desde RAMA 14): scripts npm datos:limpiar (valida los exports de CENTA y genera CSV limpios) y datos:cargar (carga en MySQL con upsert y transacción). Sin dependencias nuevas.

Nota sobre TypeScript: en backend/package.json la versión de "typescript" quedó fijada en ^5.9.0. TypeScript 7.0.2 (el nuevo compilador nativo) es incompatible con ts-node-dev a la fecha de este documento. No actualizar typescript en backend/ sin antes confirmar compatibilidad con la herramienta de desarrollo en uso.

Nota sobre versión de Prisma: al día de esta actualización, instalar el paquete "prisma" sin fijar versión (npm install prisma) resuelve a Prisma Next (línea 8.0.0-rc.x), la reescritura del ORM en Early Access, no recomendada para producción por el propio equipo de Prisma. El proyecto usa Prisma 7 (7.10.0), la línea estable y recomendada para producción actualmente. No actualizar prisma/@prisma/client sin fijar versión explícita ni sin confirmar antes en este documento, por el mismo motivo que la nota de TypeScript.

Nota sobre el generator de Prisma (desde RAMA 2): el generator prisma-client está configurado con moduleFormat = "cjs" e importFileExtension = "" (imports sin extensión). Sin esta última opción, el cliente generado hace require("./internal/class.js") y ts-node-dev falla, porque el archivo generado es .ts. No quitar esa línea de schema.prisma.

Nota sobre datos de viabilidad (CENTA): CENTA no expone API pública. Se descartó Django/web scraping en vivo como parte del stack de producción. Decisión (definida antes de RAMA 12): los datos se obtienen de la herramienta de consulta del mapa de CENTA, exportando un CSV por capa (potencial de maíz, frijol y sorgo/maicillo, y riesgo de sequía; todo Morazán, todas las clases) más la tabla de división territorial. Implementado en RAMA 14: npm run datos:limpiar valida los exports y genera CSV limpios en backend/data/centa/clean/, y npm run datos:cargar los inserta en MySQL de forma idempotente y dentro de una transacción.
Nota sobre la conexión a MySQL 8.4 (desde RAMA 10): MySQL 8.4 crea los usuarios con caching_sha2_password y, sin TLS, el conector MariaDB solo completa la autenticación si se activa allowPublicKeyRetrieval; sin esa opción las conexiones fallan en silencio y Prisma lo reporta como P2039 (pool timeout). La opción se pasa en config/prisma.ts y no como parámetro de DATABASE_URL (esa variable también la lee prisma7.config.ts y el .env no se versiona). No volver a pasar la cadena DATABASE_URL directamente al constructor de PrismaMariaDb sin conservar la opción. Detalle y diagnóstico en RAMA 10.

Estas tecnologías ya no están sujetas a cambio salvo justificación documentada aquí.

RAMA 2 — feat/auth-registro-usuario (Parte 1, Punto A del Mapa_inicial.txt: Modelo de Usuario + registro)
Responsable: Yona
Fecha: 23 de septiembre de 2026

Qué se hizo:
- Modelo Usuario agregado al final de backend/prisma/schema.prisma (bajo el comentario "Parte 1 — Autenticación"), mapeado a la tabla "usuarios" con columnas en snake_case (@map):
  - id (Int, autoincrement, PK)
  - nombres (VarChar 100), apellidos (VarChar 100)
  - correo (VarChar 255, @unique)
  - contrasena_hash (VarChar 255)
  - dui_hash (Char 64, @unique)
  - distrito (VarChar 100) — ver "Cambio respecto al Mapa"
  - verificado (Boolean, default false)
  - fecha_registro (DateTime, default now())
- Migración add_usuarios generada con npx prisma migrate dev; queda versionada en backend/prisma/migrations/.
- Hashing de contraseña: argon2id mediante el paquete argon2@0.45.1 (argon2.hash con parámetros por defecto, que ya usan argon2id). Longitud aceptada de contraseña: 8 a 128 caracteres.
- Hashing de DUI: HMAC-SHA256 con secreto de servidor (variable de entorno DUI_PEPPER), guardado como hexadecimal de 64 caracteres (Char(64)) con índice único. Justificación: un hash con sal aleatoria (bcrypt/argon2) produce un resultado distinto en cada llamada, lo que impide el índice único y la detección de un DUI ya registrado. HMAC con pepper es determinista y permite ambas cosas. Si DUI_PEPPER no está definido, el servicio lanza error explícito.
- Endpoint POST /auth/registro (backend/src/auth/registro.routes.ts), montado en index.ts con app.use("/auth", registroRouter). Recibe exactamente los campos de login_base.html, con estos nombres en el body JSON: nombres, apellidos, correo, contrasena, dui, distrito.
  - Validaciones: nombres y apellidos no vacíos (máx. 100); correo con formato válido (máx. 255), se normaliza a minúsculas y sin espacios; contrasena entre 8 y 128 caracteres; dui exactamente 9 dígitos sin guiones; distrito no vacío (máx. 100).

RAMA 10 — fix/prisma-mariadb-rsa-key (cierre de la Parte 1: verificación funcional sobre main y correcciones)
Responsable: Yona
Fecha: 3 de octubre de 2026

Contexto: RAMA 8 se mergeó sin verificación funcional por el error P2039 (ver RAMA 8, Incidencias). Esta rama ejecuta esa verificación sobre main (registro, verificación, login, GET /auth/yo), encuentra la causa real del P2039 y corrige lo detectado. Las secciones de RAMA 6 y RAMA 8 no se modifican; donde difieran de lo descrito aquí (causa del P2039, formato de errores, código de GET /auth/yo para usuario inexistente), prevalece esta sección. Causa del P2039 (resuelta):
- Síntoma: cualquier operación de base de datos fallaba con PrismaClientKnownRequestError P2039 "pool timeout: failed to retrieve a connection from pool after 10000ms (active=0 idle=0 limit=10)". Prisma oculta la causa en "cause: [Object]".
- Diagnóstico: conectar con el paquete mariadb directamente (sin Prisma) desde backend/ mostró el error real: ER_CANNOT_RETRIEVE_RSA_KEY (45044), "RSA public key is not available client side".
- Causa: MySQL 8.4 crea los usuarios con caching_sha2_password. Cuando el servidor no tiene la cuenta en su caché de autenticación (volumen o contenedor nuevo, reinicio de MySQL), exige autenticación completa y, sin TLS, el cliente necesita la clave pública RSA del servidor. El conector MariaDB solo la pide si se activa allowPublicKeyRetrieval. Sin esa opción rechaza la conexión y el pool reintenta en silencio hasta el timeout.
- Por qué no apareció en RAMA 2 a 6: hipótesis, no comprobada. Con la cuenta ya en la caché del servidor (por ejemplo tras autenticarse el CLI de Prisma con migrate) la autenticación rápida no requiere la clave. Lo comprobado es que el fallo es reproducible y afecta a cualquiera que levante el contenedor desde cero.
- El diagnóstico de RAMA 8 ("incompatibilidad del adapter MariaDB con MySQL 8.4") queda descartado: @prisma/adapter-mariadb es el adapter correcto y obligatorio (RAMA 1). Los intentos de RAMA 8 (mysql2://, regenerar secretos, reinstalar) no tenían relación con la causa.

IMPORTANTE — Pasos para clonar y levantar el entorno de desarrollo
------------------------------------------------------------
(Válido desde RAMA 2 en adelante; los pasos 2, 3 y 6 se actualizaron en RAMA 10.)

Desde la raíz del repositorio, en este orden:

1. Levantar MySQL de desarrollo:
   docker compose up -d db

2. Instalar dependencias del backend:
   cd backend
   npm install

  Si npm run dev falla con "Cannot find module 'jsonwebtoken'" (u otro paquete declarado en package.json), el node_modules local quedó incompleto: correr npm ci --legacy-peer-deps (instala exactamente lo que dice package-lock.json, sin modificarlo) y luego npx prisma generate.

3. Crear backend/.env a partir de la plantilla:
   cp .env.example .env
  Completar los dos secretos obligatorios, que la plantilla trae vacíos: DUI_PEPPER y JWT_SECRET (mín. 32 caracteres). Desde RAMA 10 el servidor NO arranca si faltan. Generar cada uno con (correr el comando dos veces):
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   Valores esperados del resto de variables (desarrollo local):
   DATABASE_URL="mysql://agroalerta:agroalerta@localhost:3306/agroalerta"
   DB_HOST=localhost
   DB_PORT=3306
   DB_USER=agroalerta
   DB_PASSWORD=agroalerta
   DB_NAME=agroalerta
   Variables agregadas después de RAMA 2 (deben existir en .env):
   EXPONER_TOKEN_VERIFICACION=true    (RAMA 5; solo desarrollo)
   JWT_SECRET=<secreto propio, mín. 32 caracteres>    (RAMA 6)
   JWT_EXPIRES_IN=2h    (RAMA 6)
   Tras un pull que modifique package.json: npm install --legacy-peer-deps dentro de backend/.

4. Generar el cliente de Prisma (sigue en backend/):
   npx prisma generate

5. Sincronizar el esquema con la base de datos:
   npx prisma migrate dev

   5b. Cargar los datos de viabilidad (desde RAMA 14; requiere el paso 5 hecho), dentro de backend/:
   npm run datos:cargar
   Carga en MySQL los CSV de backend/data/centa/clean/, que ya vienen en el repo. Es idempotente (se puede repetir). No hace falta correr datos:limpiar salvo que se actualicen los exports de CENTA. Debe terminar con: municipios 2, distritos 26, capas 4, clases_capa 12, areas_clase 312.

6. Verificar el backend:
   npm run dev
   (debe responder en localhost:3000/health; el registro responde en POST localhost:3000/auth/registro)
    Debe imprimir "Backend corriendo en puerto 3000" y /health debe devolver {"status":"ok"}. Si el puerto está ocupado, el backend aborta con "No se pudo iniciar el backend en el puerto ..." (ver con docker ps y sudo ss -ltnp | grep :3000). Si un registro falla con P2039, ver RAMA 10.

7. Frontend, en otra terminal, desde la raíz del repo:
   cd frontend
   npm install
   ng serve
   (debe responder en localhost:4200)

Nota: todos los comandos docker compose se corren desde la raíz del repo (ahí vive docker-compose.yml), nunca desde backend/. Tras cada pull que modifique schema.prisma, repetir los pasos 4 y 5. Tras cada pull que modifique backend/data/centa/clean/, repetir el 5b.

PENDIENTES (obligatorio)
------------------------------------------------------------
Cuando se cree el formulario de siembra (o registro de cultivo), debe ser más detallado y ajustado a la propuesta real:

Campos obligatorios / recomendados:
- Estado actual: Sembrado / Por sembrar
- Fecha: cuándo sembró / cuándo planea sembrar
- Qué sembró / sembrará: 3 granos principales (Maíz, Frijol, Maicillo)
- (Opcional, si se obtienen datos): tipos de semilla para cada grano
- Área sembrada / por sembrar (manzanas y/o km²)
- Cantidad sembrada / a sembrar (libras o bolsas de semilla)

Detalles sí/no:
- ¿Alquila la zona sembrada / a sembrar?
- ¿Usa maquinaria?
- ¿Usa regadío?

Inversión:
- Dinero invertido / estimación a invertir (debe incluir: semilla, venenos, fertilizantes, alquiler de tierras, mano de obra, maquinaria y sistema de riego → en general TODO)

Requerimiento adicional de lógica:
- El sistema debe poder calcular un estimado de inversión antes de que el usuario lo digite, usando:
  - Precios promedio de materiales (semillas, abonos, venenos, etc.)
  - Fórmulas por proporción de tierra
  - Redondeo hacia arriba (ej: 19.2 qq de abono → 20 qq × precio promedio)
- Mostrar al usuario: "Se estima que invirtió / invertirá aproximadamente $##" como referencia antes de que introduzca su propio valor.
- Pendiente adicional: definir cómo se obtiene y estructura la tabla de datos CENTA (zonas × granos viables) a partir de extracción manual, y quién del equipo la levanta, antes de que arranque la Parte 2.
