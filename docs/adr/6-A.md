# ADR 6-A — Sesión en el frontend: sessionStorage, interceptor y guards

- **Estado:** aceptado
- **Fecha:** noviembre de 2026 (Hito 1, Punto 6-A)
- **Contexto:** `feat/6-a-auth-login-registro`, `feat/6-a-endpoint-distritos`

## Contexto

El frontend Angular necesitaba conectarse al backend: login, registro, rutas protegidas y envío del token. El Mapa v2 dejó abierta la decisión de guardar el token “en memoria o sessionStorage”, y la de usar proxy de desarrollo o CORS.

Restricciones:

- La app se presenta en local; el backend corre en otro puerto.
- Todas las rutas usan `RenderMode.Client`, pero el proyecto conserva SSR.
- El token no debe viajar a orígenes externos.
- Un 401 debe cerrar la sesión y llevar al login con un mensaje claro.

## Decisión

1. **Token en `sessionStorage`** bajo `agroalerta_token`.
2. **Proxy de desarrollo:** `proxy.conf.json` reenvía `/api` a `http://localhost:3000`; `API_URL = '/api'`.
3. **Interceptor funcional** `authInterceptor`:
   - Agrega `Authorization: Bearer <token>` solo si la URL es del API propio.
   - Aplica un timeout de 15 s.
   - Ante 401 con token (fuera de login/registro): cierra sesión, limpia el perfil y navega a `/login?sesion=expirada|invalida`.
4. **Guards funcionales:** `authGuard` para el área con layout; `invitadoGuard` para login y registro.
5. **Vigencia del token:** `tokenVigente()` lee `exp` del JWT sin verificar la firma; un token vencido se descarta al iniciar y no cuenta como sesión.
6. **Modelos de contrato** en `core/models.ts`; los errores se traducen con `mensajesDeError()`.

## Alternativas consideradas

| Alternativa | Compromiso |
|---|---|
| Token en memoria | Más seguro ante XSS persistente, pero se pierde al recargar (F5) y obliga a reautenticar. |
| `localStorage` | Sobrevive al cierre de pestaña, pero amplía la ventana de exposición y mezcla sesiones entre pestañas. |
| Cookie `HttpOnly` | Más resistente a XSS, pero requiere coordinación de CORS, CSRF y un backend que la emita; fuera del alcance del Hito 1. |
| CORS en el backend en lugar de proxy | Válido, pero obliga a configurar orígenes en cada entorno; el proxy mantiene el frontend agnóstico. El backend ya soporta CORS opt-in para producción. |

## Consecuencias

- **Positivas:** la sesión sobrevive a F5 dentro de la pestaña; el token no se envía a terceros; el 401 se maneja en un solo lugar; el desarrollo no depende de CORS.
- **Negativas / riesgos:**
  - Un XSS podría leer el token. `sessionStorage` reduce la ventana frente a `localStorage`, pero no elimina el riesgo.
  - El logout es solo del cliente: el token sigue siendo válido en el servidor hasta expirar.
  - Si se abre la app en otra pestaña, hay que iniciar sesión de nuevo.
  - El SSR no puede usar la sesión; por eso todas las rutas son `RenderMode.Client`.
- **Operación:** en producción se reemplaza el proxy por CORS con `CORS_ORIGINS` o por un proxy inverso; el interceptor no cambia.
