# ADR 3-C — Orquestación por eventos y emisión segura

- **Estado:** aceptado
- **Fecha:** noviembre de 2026 (Parte 3, Punto C; job en 3-D y PR #44)
- **Contexto:** `feat/3-c-orquestador-clima`, `feat/3-d-endpoint-clima`, `feat/pendientes-backend`

## Contexto

La Parte 3 debía actualizar el clima de todos los distritos con coordenadas, guardar la condición y emitir eventos para que otras partes (siembra y estimación) reaccionen sin que el usuario pida un recálculo. El bus ya existía (`events/bus.ts`) y la arquitectura es EDA.

Preguntas a resolver:

- ¿Quién llama a Open-Meteo y en qué orden se guarda/emite?
- ¿Qué pasa si un listener falla?
- ¿Qué pasa si la API falla o no hay dato de lluvia?
- ¿Cómo se evita que el endpoint y el job escriban a la vez?

## Decisión

1. **Un orquestador** (`clima/orquestador.ts`) es el único punto que consulta Open-Meteo, clasifica, persiste y emite. El endpoint `POST /clima/actualizar` y el job llaman a la misma función.
2. **Orden:** consultar → clasificar → guardar → emitir. Se emite después de persistir para que un listener lea el estado nuevo.
3. **Emisión segura:** `emitirSeguro` envuelve `bus.emit` y captura el error de cualquier listener. Un listener defectuoso no deja distritos sin procesar.
4. **Una ejecución a la vez:** una promesa en cadena (`turno`) serializa las ejecuciones dentro del proceso. El endpoint y el job no escriben en paralelo.
5. **Eventos:**
   - `ActualizacionMeteorologica` en cada consulta con dato de lluvia del último día completo.
   - `CondicionClimaticaActualizada` solo cuando la condición cambia a una condición evaluada.
   - Si el último día completo no tiene precipitación, **no se emite** `ActualizacionMeteorologica`; se registra un aviso. El contrato actual exige un número.
6. **Fallos de Open-Meteo:** si la consulta falla, no se guarda nada y se conserva el último dato bueno. El job registra el error y sigue; ante un 429 pausa dos ciclos.
7. **Job periódico:** `setInterval` con intervalo mínimo de 1 hora (`CLIMA_JOB_INTERVALO_MS`), arranca con el servidor y se detiene en el cierre ordenado. La primera ejecución es después del primer intervalo.
8. **Endpoint de lectura:** `GET /clima/distritos/:id` devuelve la condición guardada, sin consultar Open-Meteo, para pintar la interfaz rápido.

## Alternativas consideradas

| Alternativa | Por qué se descartó |
|---|---|
| Emitir antes de guardar | Un listener podría leer el estado anterior. |
| Dejar que un listener lance y aborte el bucle | Un error en una parte futura impediría actualizar los distritos restantes. |
| Cola de mensajes externa (RabbitMQ, Redis) | Fuera del alcance y del stack; el bus en proceso es suficiente para la demo. |
| Consultar Open-Meteo en cada request de la interfaz | Lento, caro y sujeto a límites; la condición se guarda. |
| Job cada minuto | Supera el límite de la API y no aporta precisión. |

## Consecuencias

- **Positivas:** una sola ruta de actualización; el estado persistido es la fuente de verdad; la interfaz responde rápido; un listener roto no tumba el clima.
- **Negativas / riesgos:**
  - El bus es **en proceso**: si el proceso se reinicia, los eventos en vuelo se pierden. No hay entrega garantizada ni reintentos.
  - No hay soporte para varias instancias: cada una tendría su propio bus y su propio job.
  - El evento de actualización se omite cuando la lluvia es `null`; el contrato queda incompleto para ese caso.
  - La primera clasificación de un distrito emite cambio; falta decidir si es deseable.
- **Operación:** `CLIMA_JOB_ACTIVO=false` desactiva el job; `POST /clima/actualizar` permite forzarlo. El endpoint tiene un límite de 6 peticiones cada 10 minutos por IP.
