# ADR 1-B — Sesión JWT stateless

- **Estado:** aceptado
- **Fecha:** octubre de 2026 (Parte 1, Punto B)
- **Contexto:** `feat/1-b-login-auth-guards`

## Contexto

Después del registro y la verificación, el usuario necesitaba iniciar sesión y acceder a endpoints protegidos (`GET /auth/yo`, viabilidad y, más adelante, clima y siembra). El backend es una API Express consumida por un frontend Angular separado.

Requisitos:

- No enviar la contraseña en cada petición.
- Proteger rutas sin consultar la base en cada llamada.
- Caducar la sesión en un plazo razonable.
- Poder implementarlo sin infraestructura adicional (sin Redis, sin sesiones compartidas).

## Decisión

1. **JWT firmado con HS256** usando `jsonwebtoken`.
2. **Secreto:** `JWT_SECRET` en `.env`, mínimo 32 caracteres. El backend falla al arrancar si falta.
3. **Expiración:** `JWT_EXPIRES_IN`, por defecto `2h`. Un valor vacío se trata como ausente.
4. **Payload mínimo:** `sub` = id del usuario, `correo`. No se incluyen roles ni datos personales.
5. **Sin estado en el servidor:** `requireAuth` verifica la firma y la expiración; no consulta la base. El endpoint que necesita datos del usuario los busca por `sub`.
6. **Login uniforme:** credenciales incorrectas → 401; cuenta sin verificar → 403 **solo después** de validar la contraseña. Un hash ficticio iguala el tiempo cuando el correo no existe.
7. **Cliente:** el token se guarda en `sessionStorage` y se envía como `Authorization: Bearer <token>` (decisión de 6-A, ver `adr/6-A.md`).

## Alternativas consideradas

| Alternativa | Por qué se descartó |
|---|---|
| Sesiones en base de datos con cookie | Requiere tabla de sesiones, limpieza y coordinación con CORS; más piezas para el plazo del proyecto. |
| JWT con refresh token | Agrega un segundo token, rotación y revocación; no es necesario para una demo local. |
| Token opaco en memoria del servidor | Se pierde al reiniciar y no escala a varias instancias. |
| Guardar el token en `localStorage` | Persiste tras cerrar la pestaña; mayor ventana de exposición ante XSS. Se prefirió `sessionStorage`. |

## Consecuencias

- **Positivas:** implementación simple, sin estado compartido, suficiente para el alcance actual. El backend puede validar una petición sin tocar MySQL.
- **Negativas / riesgos:**
  - **No hay revocación:** un token robado es válido hasta que expira. El logout es solo del lado del cliente.
  - Si se cambia la contraseña, los tokens emitidos siguen vivos hasta su expiración.
  - El token vive en el navegador; un XSS podría leerlo. Se mitiga limitando el interceptor al API propio y evitando HTML no confiable, no con una solución criptográfica del lado del cliente.
  - `JWT_SECRET` debe rotarse con cuidado: rotarlo invalida todas las sesiones.
- **Operación:** el backend no arranca sin `JWT_SECRET`; el frontend descarta tokens vencidos al iniciar.
